# 任务级进展对账：第一批实现

第二批已补充持久任务、尝试及证据写入归属，使用说明见工具参考中的 `redteam_task_run`。下文保留第一批能力边界；第二批首个可执行验收条件仅覆盖 HTTP 证据记录交付，不替代漏洞真实性或通用任务验收。

基线：beta `0a478de08bb53a63bc18f808af19a98d4a81eb54`。本批只增强现有任务卡、对账与交接，不新建执行循环、不更换模型、不修改桌面安装。

## 行为

- `redteam_next_action` 对 `asset #ID` / `vuln #ID` 任务在 `focus.before.task_scope` 附加目标绑定及内容指纹。
- `redteam_progress_check` 与 `previous_task` 交接重新读取同一目标，输出 `task_progress`；全局统计和原字段仍保留。`task_measurable_change` 与原全局 `measurable_change` 分开。
- 当前目标的内容修正即使没有增加记录数，也可识别；无关目标的记录或全局分数增长，不再单独推动当前任务交接。
- 关联记录减少、目标不存在、无内容变化时暂缓核查；明确 `blocked` / `inconclusive` 的既有语义保留。
- 旧基线及其它目标类型保持原逻辑，不把未覆盖任务谎报成任务级验证。

资产覆盖原始资产行、端口、服务、指纹、关联漏洞、直接与间接关联的 HTTP 证据。漏洞覆盖原始漏洞行及其 HTTP 证据。使用 SQLite 保存点取得一致读视图，逐行计算 SHA-256，不截取前 100 条，不截断报文正文；模型只收到指纹与计数，不收到原始内容。忽略单纯时间戳与记录者元数据刷新。

## 验证范围与限制

自动测试覆盖等长证据修正、无关目标变化、全局分数增长、超过 100 条证据、删除、缺失、范围不匹配、嵌套事务、旧基线和注册工具调用链。

`task_progress.verification` 明确为 `not-performed`：记录变化不等于任务验收通过、漏洞确认、有效得分，也不能区分同一目标上的不同执行者。第二批单独输出 `task_run.assessment`，仅核对该尝试经指定写入路径创建的记录；未归属的旧记录及其它尝试记录不能作为它的交付。

未进行真实模型长任务、真实桌面验收或性能收益测量。大目标证据量对指纹耗时的影响仍需测量；流式读取不等于已证明低延迟。
